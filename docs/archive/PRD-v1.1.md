# 01. 产品概述

## 1.1 我们要做什么

「首客 FirstCustomer」是一家面向**国内想做海外生意的个人开发者、创业者和小团队**的 AI 服务公司，同时提供供客户使用的线上工作台。

客户可以带着一个想法、一款尚未上线的产品，或者已经发布却没有海外用户的工具来找首客。首客先理解客户的目标，再组织多个 MiMo Agent，围绕同一个项目协作完成研究、决策准备、推广材料、数据采集和下一步建议。

**首客的目标不是保证客户赚钱，而是让客户用更低的试错成本，更快找到值得验证的海外市场和第一批真实客户。**

## 1.2 品牌理念与产品边界

保留原版飞书方案“帮助创业者找到第一批真实客户”的理念，但**不保留单纯替客户制作一张验证页、以 ¥29 为核心商品的旧业务范围**。首客升级为“从需求到增长”的长期服务。

平台不是：

- 单纯的创业点子排行榜；
- 收入榜单或 TrustMRR 克隆站；
- 一键生成一切软件的全自动工厂；
- 保证带来付费用户的流量承诺平台。

平台真正提供的是：**有来源的市场判断 + 一套能执行的增长动作 + 真实数据回流**。

目标客户往往已经会用 AI 编程工具和免费 Skill 自己生成文案与定位，所以首客的卖点不是“生成”，而是经客户确认后替客户执行发布、接住真实回复，并交付真实反馈报告。

## 1.3 核心价值

| 客户以前遇到的问题 | 首客要交付的价值 |
|---|---|
| 想出海，但不知道市场需要什么 | 提供有原始证据的需求机会及竞品信息 |
| 有产品，却不清楚第一批客户是谁 | 聚焦一个明确的海外细分客群（ICP） |
| 不会做英文定位和市场宣传 | 产出英文卖点、落地页和可编辑推广素材 |
| 不知道从哪个渠道开始获客 | 推荐适合目标客户的一个低成本渠道，规划真实实验 |
| 做过推广却看不懂效果 | 汇总真实访问、报名和付费数据，提出下一轮行动 |

## 1.4 一眼能理解的业务闭环

**创建项目 → AI 研究市场 → 老板把关、客户确认方向 → 生成英文验证页 → 人工批准推广 → 收集真实反馈 → AI 复盘 → 决定下一步。**

其中“AI 研究到反馈复盘”由多个 Agent 分工；涉及支出、对外发布和重大商业判断时，人必须确认。

# 02. 客户是谁，先服务谁

## 2.1 四类目标客户

| 用户阶段 | 典型说法 | 主要需求 | 产品应提供 |
|---|---|---|---|
| A. 还没有产品 | “我会开发，但不知道海外什么需求能赚钱” | 找方向 | 海外需求清单、竞品与价格、机会优先级、MVP 建议 |
| B. 有想法或原型 | “我想做这个产品，不确定有人愿意买” | 验证方向 | 细分客户、核心痛点、需求验证实验 |
| C. 有 MVP 或已上线 | “产品做好了，但没有海外用户” | 找到第一批客户 | 英文定位、公开验证页、推广素材、转化跟踪 |
| D. 已有一些用户 | “有流量但没人付费” | 提升转化 | 漏斗分析、渠道复盘、定价与文案实验 |

## 2.2 比赛期间只聚焦一类客户

**首期优先客户：已有可演示产品或 MVP，但尚未获得稳定海外用户的中国独立开发者。**

选择原因：

1. 已经有产品，不必在 40 小时内替客户重新开发复杂软件；
2. 可以很快给出真实英文页面与可访问链接；
3. 可以用真实访问和留资反馈来验证服务交付；
4. 容易在有限时间里演示“需求 → 上线 → 数据”的完整过程。

“没有产品、想寻找赚钱机会”的用户也能留下需求，但比赛版本先生成**机会研究与验证计划**，不承诺自动开发完整 SaaS。完整产品孵化与代码 Agent 接入放在后续版本。

## 2.3 用户最希望完成的任务

**用户故事 U-01：** 作为已经有 MVP 的开发者，我想知道我的产品在英语市场应该先卖给谁，这样我不需要盲目投广告。  
**用户故事 U-02：** 作为准备出海的创业者，我想看到真实需求和同类产品的付费信号，避免被 AI 编出来的“热门机会”误导。  
**用户故事 U-03：** 作为没有营销团队的开发者，我希望有人帮我把定位变成英文页面与首轮推广素材。  
**用户故事 U-04：** 作为服务购买者，我希望知道 Agent 当前在做什么、哪些决策需要我确认、最终交付是否有效。  
**用户故事 U-05：** 作为首客的经营者，我需要知道真实订单收入、交付成本和客户反馈，才能判断这家 AI 公司是否能运营。

# 03. 产品如何服务客户

## 3.1 五阶段服务链路

### 阶段一：Discover｜发现海外需求

**解决的问题：** 这个市场真的存在痛点吗？

输入：客户的行业/技能/产品描述、目标国家、预算。  
工作：查看合规来源中的公开反馈、用户问题、竞品产品介绍和官方定价。  
输出：三个候选细分市场、各自的支持证据与反面证据，以及一个优先研究的方向。  
必须说明：**竞品定价证明它在收费，不代表它已经赚到了多少钱。**

### 阶段二：Validate｜验证有没有商业机会

**解决的问题：** 什么人可能愿意付费？怎样低成本验证？

输入：研究结果、客户产品资料。  
工作：比较目标客群、替代方案、收费模式、可接触的用户群体。  
输出：用户画像、价值主张、价格假设、最小验证实验（含预设判定条件和最小样本），以及对反面证据的回应。  
关键决策：首客老板把关并推荐，客户确认首期服务的细分人群及实验目标（见 5.8）。

### 阶段三：Position & Build｜准备产品与英文市场材料

**解决的问题：** 如何让海外用户一眼看懂这是什么、为什么值得试？

比赛版本：生成一张**真实可访问的英文产品验证页**，包含产品价值、典型场景、行动按钮、反馈/留资表单和基础埋点。页面上的事实声明必须绑定证据，检查通过后才能送审（见 5.6）。  
长期版本：进一步输出 MVP PRD，并在获得客户明确授权后接入代码仓库、自动化测试与预览部署；不把复杂代码开发作为比赛第一版承诺。

### 阶段四：Launch｜启动第一个海外获客实验

**解决的问题：** 第一批用户从哪里来？

由 Agent 推荐 **一个**与细分客群匹配的渠道（例如 Product Hunt、特定开发者社区、X 或 SEO 页面），准备 2–3 条可编辑素材及发布检查清单。素材中的事实声明同样要绑定证据。  
老板把关、客户确认后再发布；若无法安全、合规地自动发布，提供可复制素材和人工发布记录即可。  
不做批量垃圾私信、刷量、冒充用户或绕过平台限制。

### 阶段五：Grow｜根据真实反馈调整

**解决的问题：** 这次实验说明了什么？下一轮该改哪里？

收集第一方页面访问、点击、表单提交、真实回复和评论，以及客户自愿提供的试用/付费记录。  
Agent 生成一页复盘：原定假设、做过的动作、真实回复和评论、实际数据、仍不确定的地方、下一步建议。样本未达到预设标准时，结论写“样本不足”，不能说假设已被证实或否定。  
**没有流量就显示零，没有付费就显示零；绝不把报名当作收入。**

## 3.2 两条典型客户路径

**路径 A：客户已有产品（比赛重点）**

1. 客户粘贴产品链接，选择“想要第一批海外用户”。
2. 首客自动整理产品与需求信息，必要时追问关键问题。
3. 研究 Agent 给出两个可能的海外细分人群，以及支持和反面证据；证据不足时，策略 Agent 打回补查。
4. 老板把关并推荐，客户确认目标人群、渠道与页面内容。
5. 首客上线英文验证页，得到可公开访问的地址。
6. 客户批准一项真实推广实验，记录实际发布时间。
7. 首客收集访问及报名，生成有证据的复盘报告。

**路径 B：客户还没有产品（赛后逐步完善）**

1. 客户填写擅长技术、可投入时间、预算、目标月收入。
2. 首客筛选海外需求及收费竞品，给出机会候选。
3. 客户选择一个机会，获得 MVP 功能清单和验证路径。
4. 先用落地页、访谈或预售测试验证，再决定是否开发。
5. 项目具备基础证据后，转入 Build / Launch / Grow。

## 3.3 对外服务交付物

一次标准“出海启动任务”至少包含：

- **定位卡：** 产品卖给谁、要解决的一个关键问题、价值主张；
- **商业证据卡：** 需求来源、竞品官方定价、付费证据的等级及缺失项、主要反面证据及回应；
- **英文验证页：** 可访问链接、有效 CTA、留资或反馈表单，事实声明可追溯到证据；
- **渠道行动卡：** 一个优先渠道、两到三条推广素材、执行时间与确认状态；
- **结果简报：** 真实回复和评论、实际访问、留资、访谈反馈、尚未验证的假设、下一步计划。

这五件东西是服务成果，也是比赛现场最容易验收的证据。

# 04. 产品页面与交互要求

**比赛第一版只做三个核心业务页面**（首客官网、客户项目页、公司经营台），另外按模板生成客户的公开英文验证页。长期可以扩展导航，不在现场追求复杂控制台。

## 页面 P-01：首客官网（公开）

**目的：** 让国内创业者在 30 秒内知道首客提供什么服务，愿意发起一次出海任务。

必须有：一句话价值说明、适合谁、完整服务流程、真实演示样例、清晰的服务边界、报价或咨询入口、隐私与联系入口。  
主按钮：“开始我的出海验证”。  
成功标准：访客可以从首页进入新建项目或咨询下单，不发生死链。  
注意：尚未服务过的客户案例必须标注“示例”，不能伪造成交。

## 页面 P-02：客户项目页（项目专属链接）

**目的：** 用最少的信息启动服务，并把进度、待确认决策和 Agent 产出放在同一页。V1.0 的 P-02 和 P-03 在比赛版本合并为这一页。

**访问方式：** 客户不用注册登录，通过不可猜的项目专属链接访问；老板可以作废并重新生成链接。

### 新建项目

客户首次填写：

| 字段 | 是否必填 | 说明 |
|---|---|---|
| 当前阶段 | 必填 | 没有产品 / 有想法 / 已有 MVP / 已上线 |
| 产品名称或想法 | 必填 | 一两句话即可 |
| 产品网址 | 选填 | 已有产品时建议填写 |
| 希望进入的市场 | 选填 | 可选“请 AI 帮我判断” |
| 当前最想解决的事 | 必填 | 找需求 / 验证 / 找首批用户 / 提升转化 |
| 预算和时间 | 选填 | 用来约束 Agent 建议 |
| 联系方式 | 必填（提交服务订单时） | 用于交付与必要联系 |

提交后显示：项目概况、Agent 工作进度、当前需要确认的决策、交付物清单、订单/报价状态。  
关键规则：信息不够时最多优先追问三个关键问题；已填写的内容应保存，不能让客户重来。

### 项目工作区

**目的：** 把 Agent 的研究、内容制作和增长执行放在同一个地方。

建议模块：

1. **市场证据：** 每条结论旁展示来源、时间、证据等级和“已验证/待验证”状态，支持证据和反面证据分开展示。
2. **策略确认：** 展示最多两个定位方案、选择原因及对反面证据的回应；老板把关后由客户确认，按钮“确认采用”或“退回修改”。
3. **英文页面：** 展示预览链接、上线状态、真实公开 URL，以及事实声明与证据摘录的对照。
4. **渠道任务：** 展示文案、目标渠道、人工审批、发布时间。
5. **增长数据：** 展示访问、有效线索、试用和实际付费，注明统计口径。
6. **交付报告：** 可以复制或导出，所有数据都有来源。

关键规则：客户的数据和项目与其他客户隔离；未发布内容不能被外部随意访问；作废的项目链接不能再看到任何数据。

## 页面 P-04：首客 OPC 公司经营台（管理员）

**目的：** 让比赛评委看到“一人公司真的在运营”，让经营者知道每笔业务的进展和成本。

必须展示：

- 客户线索、咨询单、服务订单、已支付/未支付状态；
- 各订单正在执行的 Agent、任务耗时、失败、重试和打回记录（谁打回谁、原因、结果）；
- 待老板批准的决定、预算、对外发布动作、等待客户确认的事项，以及超过打回上限、需要老板裁决的事项；
- 交付情况、模型调用成本（按标价折算，赛事赞助的部分要标注）、每单老板人工分钟、客户反馈；
- **首客自身收入**与**客户项目增长数据**两套独立统计。

重点设计：“待我决定”优先于聊天日志。老板能够暂停、批准、拒绝和重新指派一项任务。

## 公开生成页 P-05：英文产品验证页（模板生成）

**目的：** 接受真实海外访客访问与反馈。

页面至少包含：英文标题、产品价值主张、使用场景、清晰 CTA、联系方式/表单、必要的隐私说明。  
地址示例：`/launch/your-product`，实际使用唯一 slug。  
必须能正常打开、正确记录事件、成功提交表单；不能只是设计预览图。

# 05. MiMo Agent 团队如何工作

## 5.1 四名 AI 员工 + 一名人类老板

| 角色 | 简单理解 | 负责完成的工作 | 主要交付 |
|---|---|---|---|
| Research Agent | 市场研究员 | 发现需求、阅读竞品、记录价格与证据 | 需求报告、证据卡 |
| Strategy Agent | 出海产品经理 | 确定细分客户、价值主张、验证方法与预算 | 定位方案、实验计划 |
| Launch Agent | 英文营销与发布专员 | 准备页面、英文文案与渠道发布任务 | 验证页、推广素材 |
| Growth Agent | 数据分析与复盘专员 | 汇总真实数据、评价实验、建议下一步 | 复盘简报、下一轮行动 |
| Founder（人类） | 公司老板 | 决定报价、预算与特殊情况；把关并推荐方向和对外内容 | 把关记录、经营结果 |
| Customer（人类） | 服务购买者 | 确认定位、对外内容和下一轮实验 | 确认记录 |

**技术创新要点：** 不是让四个机器人轮流聊天，而是每个 Agent 都有真实的输入、工具、产出和交接记录。一个阶段不符合要求，不能直接进入下一阶段，而要带着具体要求打回上游（见 5.5）。

## 5.2 具体协作示例

客户说：“我有一款 AI 会议纪要产品，想卖到北美。”

Research Agent 发现“所有知识工作者”这个人群太宽，给出有来源的两个候选细分市场，并分别列出支持证据和反面证据。Strategy Agent 发现“远程咨询团队”的付费意愿证据不足，打回 Research 补查同类产品的定价页和差评。补查后，Strategy Agent 判断这一人群更容易接触，回应了“小团队嫌贵”这条反面证据，并提出两个方案。系统把这件事交到老板工作台：**“要先服务远程咨询团队，还是全部中小企业？”** 老板把关并推荐后，再交给客户确认。

客户确认“远程咨询团队”后，Launch Agent 才能继续生成针对这一人群的英文落地页和宣传材料。文案里“每周节省 5 小时”这句话找不到来源，程序不允许送审，Launch Agent 必须换掉它或请求补证据。Growth Agent 后续只分析这个版本的真实实验数据。

**Agent 因证据不足打回**和**人类决策改变 AI 后续执行**，这两处应当成为参赛 Demo 的重点。

## 5.3 必须遵守的协作规则

1. **有依据才下结论。** 证据不足时必须输出“尚未验证”，不能杜撰用户痛点、收入和转化。
2. **风险动作要有人确认。** 付款、外部发布、批量联络、修改正式网站、接触敏感数据前，都需要明确授权和审批。定位和对外内容由老板把关、客户确认（见 5.8）。
3. **失败不能让订单消失。** Agent 出错要保留已完成部分，允许有限重试，并明确失败原因。
4. **不合格就打回。** 下游发现输入不足时要写明缺什么，不能自己猜着补；打回次数有上限，超过后交给老板。
5. **先找反证再下结论。** 每个候选方向都要查反面证据，找不到也要记录查过什么。

## 5.4 一笔项目的状态

`已提交 → 研究中 → 制定策略 → 等待定位确认 → 准备页面 → 等待发布确认 → 已发布 → 收集反馈 → 分析复盘 → 已交付`

回退路径：`制定策略 → 研究中`（证据不足）、`准备页面 → 制定策略`（卖点缺证据）、`分析复盘 → 制定策略`（老板和客户批准开启下一轮）、`等待定位确认 → 制定策略`（老板或客户退回）、`等待发布确认 → 准备页面`（老板或客户退回）。

`等待定位确认` 和 `等待发布确认` 都包含老板把关和客户确认两步。

异常状态：`等待补充信息`、`执行失败（可重试）`、`等待老板裁决`（打回超限）、`已取消`。  
状态变化要记录时间、执行者、相关成果和人工决定，不能只在聊天记录里表现。

## 5.5 Agent 之间怎样打回

打回不是让 Agent 自由聊天，而是一次有固定字段、次数上限和运行记录的流转。

| 路线 | 什么时候触发 | 打回时必须写明 | 到上限后 |
|---|---|---|---|
| Strategy → Research | 支撑决策的证据不足，或反面证据尚未核实 | 要补查的具体问题、需要的来源类型 | 老板决定：按“尚未验证”继续，或换方向 |
| Launch → Strategy | 要用的卖点没有证据，或与已批准的定位冲突 | 涉及的声明、缺少什么证据 | 老板决定：删除卖点、换卖点或补证据 |
| Growth → Strategy | 达到预设最小样本，且结果未达到预设判定条件 | 原假设、实际数据、建议调整的假设 | 写入结果简报，由老板把关、客户确认是否开启下一轮 |

**实现规则：**

1. Agent 的输出统一包含 `status`（`done` 或 `need_more`）和 `request`（缺什么、为什么需要）。Agent 只能提出请求，下一步由状态机决定，不能自己调用其他 Agent。
2. 前两条路线同一阶段各最多打回 2 次，Growth → Strategy 每轮实验最多 1 次。前两条路线超过上限后停止调用模型，进入 `等待老板裁决`。
3. 补查时只追加证据，不覆盖已有结果；每次打回都写入 `agent_tasks`，记录上游任务、原因、轮次和结果。
4. 如果打回后定位发生变化，老板和客户之前的确认都失效，必须重新进入 `等待定位确认`；旧定位生成的页面不能发布。只更换支撑卖点、定位不变时，不用重新确认定位，但发布前仍要确认页面。
5. 下一轮实验必须经老板把关、客户确认，不能自动修改已发布页面或自动发布新内容。样本不足时结论写“样本不足”，不触发打回。

## 5.6 证据闸门：对外声明必须有证据

证据闸门由程序执行，不靠模型自己判断，一共两道。

**第一道：证据入库。** 来源链接、采集时间和引用摘录必须齐全，引用摘录要能在采集到的来源文本中找到；否则不能作为“已验证”证据入库。

**第二道：页面和素材送审前。** Launch Agent 输出的每条事实声明都要带 `evidence_id`。程序检查：

1. 声明绑定了证据，证据存在，且本项目有权使用；
2. 证据的许可状态允许对外使用；
3. 页面中的数字和百分比只能出现在已登记的声明里；模板的其他文案位置出现数字时直接报错。

| 内容类型 | 例子 | 是否需要证据 |
|---|---|---|
| 数字或效果 | “每周节省 5 小时” | 需要 |
| 竞品对比 | “比某产品便宜 30%” | 需要 |
| 用户痛点 | “咨询师常为写会议纪要加班” | 需要 |
| 产品功能 | “支持 Zoom 录音” | 需要，可登记为“客户提供”并写明日期 |
| 价值主张和行动号召 | “把会议变成可交付的客户纪要”“Start free” | 不需要 |

检查不通过时不能进入 `等待发布确认`，系统要指出是哪条声明，退回 Launch Agent 修改；仍然缺证据时，按 5.5 打回 Strategy。

**程序做不到的部分：** 程序只能确认证据存在，不能完全判断证据是否真的支持这句话，也可能漏掉不含数字的事实声明。因此老板把关和客户确认发布时，页面要并排显示每条声明和证据摘录，由人做最后判断。

公开页面不要求展示全部来源；声明和证据的对应关系保存在后台，并写入交付报告。

## 5.7 主动寻找反面证据

Research Agent 不能只搜支持当前方向的材料。

1. **反向检索：** 每个候选人群至少做一轮，查差评、放弃或退订原因、价格抱怨、替代方案和竞品关停情况。
2. **分开记录：** 每条证据标记 `stance`（支持、反面或中性）。
3. **如实记录空结果：** 没找到反面证据时，记录检索词、范围和时间，写“已检索，未发现”，不能写“没有风险”。
4. **必须回应：** Strategy Agent 要回应每条反面证据，可以合并回应。回应方式只有三种：接受并调整方案、用其他证据反驳、列为实验待验证。
5. **程序检查：** 有反面证据未回应时，不能进入 `等待定位确认`。老板和客户在确认页面能同时看到证据和回应。

## 5.8 谁有权确认什么

真实客户的定位和对外内容应由客户确认，所以审批分两道：老板把关并推荐，客户确认。

| 事项 | 老板 | 客户 |
|---|---|---|
| 目标人群和定位 | 把关并推荐 | 确认 |
| 英文页面和渠道素材 | 把关 | 确认后才能发布 |
| 下一轮实验 | 把关并推荐 | 确认 |
| 报价、退款和首客自身预算 | 决定 | 接受或不接受报价 |
| 打回超限 | 裁决 | 影响定位或对外内容时仍要确认 |

1. `decisions` 表用 `actor_role` 记录决定来自老板还是客户，两道审批分开记录。
2. 任意一方退回，项目都回到上一步，不能继续发布旧版本。
3. 客户没有确认时，项目停在等待状态，不能自动发布。赛前要和客户约好比赛周末能在线确认的时段。
4. 用自有产品兜底时，老板同时担任两个角色，但两道记录都要保留，并标注“自有产品”，不能算作外部客户确认。

# 06. “赚钱需求雷达”怎样融入首客

## 6.1 不是一个独立收入榜，而是研究能力

沿用 TrustMRR 带来的启发：**判断商业机会时，尽量查找真实的付费信号，而不只是看讨论热度。**

Research Agent 研究一个机会时，要分别记录五类信息：

| 信号 | 代表什么 | 正确的呈现方式 |
|---|---|---|
| 真实痛点 | 用户明确表达过什么困难 | 附原始帖子/采访记录和日期 |
| 付费竞品 | 有人正在销售同类解决方案 | 展示官网和定价，不等同收入 |
| 收入资料 | 公开披露或有权使用的收入记录 | 按 6.4 标注付费证据等级，并写明口径和日期 |
| 可获客渠道 | 潜在客户聚集在哪里 | 提供具体渠道及触达限制 |
| 反面信号 | 用户为什么不买、放弃或不满 | 附原始来源和日期；没找到时写明检索范围 |

**关键边界：** 不把 TrustMRR 或其他服务的数据直接无授权批量抓取、重发布为商业数据库；优先使用获得许可的数据源、竞品官方公开信息、客户授权素材以及原创访谈。技术上必须保留来源和采集日期。

## 6.2 机会卡的最低字段

机会名称、目标用户、用户原始问题、竞品名称与官方价格、市场证据来源、付费证据等级、主要反面证据及回应、可能的差异化、验证方法、数据时间与待确认事项。  
第一版不强制做“综合 92 分”的神秘评分；有证据的判断比漂亮分数重要。

## 6.3 机会雷达的两个用途

- **对外帮助客户：** 在需求分析或市场定位时，提供可核验的商业判断。
- **对内帮助首客：** 发现哪些开发者正在为出海定位和获客发愁，指导首客写内容和选择服务主题。对外联系需人工审核且遵守平台规则。

## 6.4 付费证据等级

“收入未知”不能作为默认结果。判断重点从“收入多少”改为“付费证据有多强”，只有所有来源都查不到时才显示“未知”。

| 等级 | 含义 | 例子 |
|---|---|---|
| A | 支付数据验证 | 客户授权的支付后台数据；TrustMRR 也属此类，但 P0 不接 |
| B | 交易平台披露 | Microns、Acquire、Flippa 的公开挂牌 |
| C | 创始人公开说法 | GetLatka 访谈、Starter Story、Indie Hackers |
| D | 第三方估算 | 必须标明是估算 |
| E | 只有付费信号 | 官网有付费方案和定价 |
| 未知 | 以上都没有 | 只有这时才显示 |

比赛期大多数竞品卡会是 E 级，可以叠加多个信号，例如“官网有付费方案，App Store 有若干条评分，收入未公开”。

使用时要遵守四条规则：

1. **信号不等于收入：** 评分数和下载量要标明是信号，不是付费用户或收入。
2. **数字不取平均：** 来源之间不一致时并列显示。
3. **口径不混用：** MRR、过去 12 个月收入和年收入不能直接比较。
4. **注意幸存者偏差：** 这些网站只收录愿意公开或正在出售的产品，不能用来判断市场规模或成功率，卡片上要写明。

## 6.5 证据从哪里来

比赛期不使用付费商业 API，也没有现成的收入数据库可以下载。证据库由首客自己逐条积累，每条都公开来源，不建隐藏来源的数据库。

| 要证明什么 | 来源 | 接入方式 |
|---|---|---|
| 用户真的有痛点 | HN Algolia、GitHub Issues、Stack Exchange、dev.to | 免费 API，有频率限制 |
| 竞品在收费 | 竞品官网定价页 | MiMo 联网搜索或读取页面；需要渲染时用 Crawl4AI |
| 收费持续多久 | Wayback 历史快照 | 免费 API |
| 移动端需求量 | iTunes Search API | 免费 API |
| 开发者工具热度 | npm 下载量 API、GitHub 星数 | 免费 API |
| 收入数字 | Microns、Starter Story、GetLatka 的公开页面 | 人工录入少量事实和链接，不批量复制 |
| 真实收入 | 客户授权的数据 | 客户提供 |

以上免费接口已在 2026 年 11 月 2 日试过，可以调通；官网价格能否自动解析还没有测试。

**P0 不接入：** 付费商业数据 API（如 Netrows、Similarweb、Ahrefs）；TrustMRR API（条款和是否收费都未确认）；Reddit API（需事先批准，商业用途需书面批准）；GitHub 上抓取来的数据集（如 `trustmrrr-db`）。

## 6.6 证据库和查询顺序

证据库就是 `evidence_items` 这张表。每次查询按这个顺序走：

1. 查本地证据库，有未过期的记录就直接用；
2. 没有就查免费来源和 MiMo 联网搜索，通过第一道证据闸门后入库；
3. 还查不到，由老板粘贴链接和数字，同样要过证据闸门；
4. 都没有，才显示“未知”。

Agent 不直接读写数据库，只调用两个工具，这样它没办法把自己编的内容写进库里：

- `lookup_evidence`：按产品或品类查本地未过期的记录；
- `search_evidence`：本地没有时检索来源，程序核对后才写入。

**有效期：** 定价 7 天，收入 30 天，过期后要重新核对。

**赛前种子：** 确定第一位客户后，手工录入这个品类的 20–30 条证据，保证现场搜索不稳定时流程也能走通。

**存储边界：** 只存实际用到的条目，不复制别人的整张表。

**长期壁垒：** 客户授权的经营数据、访谈记录和首客每次实验的结果，这些是别人拿不到的数据。

# 07. 商业模式与订单规则

## 7.1 首客卖什么

第一阶段主要通过**标准化交付服务**赚钱，而不是等平台有大量用户之后才卖会员。

| 服务 | 建议测试价格 | 客户获得什么 | 上线阶段 |
|---|---:|---|---|
| 免费出海初诊 | 免费 | 简短问题诊断与下一步建议 | 比赛 P0 |
| 海外市场验证 | ¥99 / 次 | ICP、需求证据、竞品分析、验证计划 | 比赛可选收费 SKU |
| 首客启动包 | ¥299 / 次 | 市场验证 + 英文验证页 + 推广素材 + 首轮数据简报 | 比赛重点展示服务 |
| Growth Copilot | 待测，建议按月收费 | 持续追踪数据、规划实验、复盘增长 | 赛后 |

**价格为测试假设，不代表市场已经验证。** 比赛时建议只正式销售一款范围清晰的服务，避免承诺“无限增长代运营”。

可以测试一条服务承诺：**没有按约定完成发布就退款。** 这只保证动作，不保证结果，不违背 1.2 的产品边界。

## 7.2 服务订单与客户项目是两套不同东西

- **服务订单：** 客户向首客购买的服务。包含报价、付款状态、交付物、验收与退款记录。
- **客户项目：** 首客帮助这个客户推广的产品。包含验证页访客、报名、试用和该产品自己的付费结果。

两套数据不可混合。例如：某验证页获得 12 个报名，并不等于首客成交 12 单，也不能说客户已获得 12 位付费用户。

## 7.3 首单证明什么

比赛希望争取一个真实客户，最好有真实支付记录；但**支付成功取决于实际客户和支付系统情况**，不能预先写进成果。若尚未成交，只能如实展示“真实询盘 / 已报价 / 客户试用 / 交付成功”，模拟交易需明显标注。外部客户没有到位时，可以用自有产品跑通流程，但必须标注“自有产品”，不能算作外部客户或收入。

完整交付记录包括：客户确认的需求、实际报价、Agent 执行日志、可访问的交付页面、真实反馈，以及付款或未付款状态。

# 08. 第一版范围与开发优先级

## 8.1 P0：比赛期间必须完成

| 功能编号 | 功能 | 必须达到的验收结果 |
|---|---|---|
| FC-01 | 官网与新建项目 | 能创建并保存一位真实客户的项目 |
| FC-02 | 需求输入与基本澄清 | 客户能确认产品、目标、市场和预算 |
| FC-03 | Research + Strategy Agent | 生成有真实来源的定位建议，包含反面证据及回应；证据不足时能打回补查，并能请求老板把关和客户确认 |
| FC-04 | Launch Agent + 英文页模板 | 生成真实可访问的英语验证页及可用表单；事实声明未绑定证据时不能送审 |
| FC-05 | 一项实际推广动作 | 有审核通过的文案和真实发布/执行记录 |
| FC-06 | Growth Agent 数据复盘 | 能展示真实访问和线索，数据为空时显示零；样本不足时如实说明 |
| FC-07 | 公司经营台 | 展示订单、支付状态、Agent 任务、成本、老板人工分钟及待审批事项 |
| FC-08 | 证据链与错误恢复 | 能看原始来源、证据等级、审批和打回记录；失败可重试，不重复发布 |

## 8.2 P1：赛后第一轮（2–4 周，可调整）

为“无产品用户”增加更完整的赚钱需求雷达、系统化竞品研究、多套页面模板、邮件跟进、搜索渠道数据整合、客户自助结账、客户账号登录，以及团队更稳定的权限管理。

## 8.3 P2：有真实付费后再做

自动化多渠道运营、跨平台授权连接、代码仓库辅助开发、广告预算管理、多语言市场、本地化支付、更多验证渠道，以及基于长期实际数据的增长推荐。

## 8.4 明确暂时不做

全网爬虫、未经授权的 MRR 数据库和隐藏来源的证据库；比赛期接入付费商业数据 API 或 Reddit API；更多 Agent 角色、Agent 自由对话、动态任务规划、长期记忆、向量库和多模型投票；自动代发所有社交平台；一键建完整复杂 SaaS；多层级代理商系统；任何收益保证；炫酷但不影响订单闭环的三维可视化。

# 09. 技术方案（尽量少造轮子）

## 9.1 推荐技术结构

| 部分 | 建议方案 | 为什么这样选 |
|---|---|---|
| Web 界面 | Next.js / React 或团队现有熟悉框架 | 快速做出可访问产品和英文页面 |
| 用户与业务数据库 | PostgreSQL（与 Web 同机）或团队现有数据库 | 保存项目、订单、证据、任务与日志 |
| 核心 AI | Xiaomi MiMo API：四个 Agent 的主要产出用 `mimo-v2.6-pro`，字段提取和 JSON 修复用 `mimo-v2.6-flash`，模型名写进配置 | 满足赛事主线，执行研究、策略与内容生成 |
| Agent 编排 | OpenAI SDK 连接 MiMo + 自写工具循环 + 状态机 + 有上限的打回路由（见 9.4） | 易调试、可恢复，避免盲目堆复杂框架 |
| 市场研究 | 自建证据库 + 免费来源 + MiMo 联网搜索（见 6.5、6.6） | 来源清楚，不依赖付费 API 和未经许可的海量数据 |
| 页面发布 | 固定英文模板 + 动态内容 | 确保页面和表单真实可运行 |
| 增长统计 | 第一方服务端事件；可按需使用 Umami | 流量、留资可核验 |
| 资料交付 | 在线报告 + Markdown/打印导出 | 现场易展示，后续可升级 PDF |
| 部署 | 一台香港或新加坡 VPS + 自有域名，统一运行 Web、数据库和 Agent worker | 大陆服务器建站通常要 ICP 备案，来不及；页面要在北京现场和美国都能打开；长任务放 serverless 容易超时 |

开源组件的比赛期用法：GPT Researcher 和 LangGraph 不接入；Crawl4AI 只在页面需要渲染、普通方式读不到时使用；Umami 可选，因为第一方 `events` 表反正要做。优先使用自己已经熟悉的技术。

可以参考的项目（都没有运行过代码）：gtm-cofounder（研究流程）、FounderOS（经营台，演示数据和真实数据分开）、mission-control（“待我决定”和成本追踪）、marketingskills（Launch 文案素材）。

第三方组件接入前必须核对许可证与数据使用规则。`chadboyda/agent-gtm-skills` 和 `irinabuht12-oss/marketing-skills` 在 GitHub 上没有显示许可证，不要复制。

## 9.2 必要业务数据

不要求比赛现场把每个字段做得很复杂，但至少要保存：

- `users`：经营者账号；客户在比赛版本通过项目专属链接访问，不用注册；
- `projects`：客户产品、目标市场、预算、当前阶段、项目链接令牌、是否自有产品；
- `orders` / `payments`：首客自身服务报价、收款状态和每单老板人工分钟；
- `agent_tasks`：哪个 Agent 做什么、实际使用的 `provider` 和 `model`、输入输出、时间、成本、错误，以及上游任务、打回原因和轮次；
- `evidence_items`：产品、数字及口径、原始来源、采集时间、过期时间、引用摘录、立场（支持/反面/中性）、付费证据等级与许可状态；
- `claims`：页面或素材中的事实声明、绑定的证据和检查结果；
- `counter_responses`：Strategy 对反面证据的回应（接受、反驳或待验证）；
- `decisions`：客户或老板的批准、拒绝与原因，用 `actor_role` 区分身份；
- `landing_pages`：英文页内容、公开 URL、发布状态；
- `campaigns` / `events`：发布渠道、访问、点击、留资、回复和评论等真实事件；
- `deliverables`：最终报告及版本。

## 9.3 稳定性与安全底线

1. 模型输出按固定字段校验，不符合要求时提示重试，不能写入错误业务数据。MiMo 文档只提供 `json_object` 模式，不校验字段结构，所以要用 Zod 等工具自己校验，并把 `max_completion_tokens` 设够。
2. 模型失败时保存当前进度，允许人工恢复；同一任务重试不得重复收费、重复发布。
3. 对外发布、预算支出、连接第三方账号都需要明确授权。
4. 网站收集邮箱等信息时给出用途说明，限制访问并支持必要的数据删除；目标地区的具体法律要求应按实际市场核对。
5. 研究材料中的网页内容不能当作系统指令；Agent 不得越权访问其他客户数据。
6. 没有来源的商业判断必须标注“假设”，没有数据的运营结果必须显示真实的零或未知。
7. 打回路由、声明检查和反面证据检查由程序执行。Agent 没有发布、扣款和修改项目状态的工具，只能提交结果和请求。

## 9.4 Agent 和模型调用

比赛版本不引入额外的 Agent SDK。用 OpenAI SDK 连接 MiMo（`https://api.xiaomimimo.com/v1`，Key 放在环境变量 `MIMO_API_KEY`），自写工具循环和状态机。

每个 Agent 就是一段配置：角色提示词、可用工具和输出格式。

| Agent | 可用工具 | 是否多轮调用 |
|---|---|---|
| Research | `lookup_evidence`、`search_evidence`、读取网页 | 是，设最大轮数 |
| Strategy | 只读证据 | 通常一次，不够时走打回 |
| Launch | 只读已确认的决策 | 通常一次，声明检查不过时改写 |
| Growth | 只读真实访问、线索、回复和评论 | 通常一次 |

**模型使用规则：**

1. 所有模型调用走统一的 `callModel()`，切换服务只改 `base_url` 和模型名，并把实际使用的 `provider` 和 `model` 写入 `agent_tasks`。
2. 面向客户的 Agent 产出都走 MiMo。其他 AI API 只用于开发辅助和 MiMo 故障时的临时备用；备用时要在经营台显示实际模型，不能说成 MiMo。
3. MiMo 联网搜索的文档写明只支持 Chat Completions 协议，所以比赛版本统一用这个协议。
4. 按 `usage` 和 `web_search_usage` 记录用量，成本按标价折算显示；由赛事赞助的部分要标注，不能把每单成本写成 0。
5. P0 除文本外，使用带引用的联网搜索和图片理解（读取客户产品和竞品截图）；时间够再接语音识别，把访谈转成证据。

# 10. 测试与验收标准

下表是开发者做完以后，产品负责人可以直接拿着检查的内容。

| 编号 | 验收场景 | 通过标准 |
|---|---|---|
| AC-01 | 新客户创建项目 | 填写最少必填信息即可保存，刷新后内容仍在 |
| AC-02 | 研究竞品和需求 | 关键结论可打开来源，来源和日期清楚；未知内容不装作已验证 |
| AC-03 | 老板或客户否决定位 | Agent 不继续发布旧方向，任务正确返回修改状态 |
| AC-04 | 发布英文页面 | 在无登录状态下可以打开，主按钮与表单真实可用 |
| AC-05 | 测试提交意向表单 | 服务端收到数据，页面提示成功，后台能查看，重复提交有基本防护 |
| AC-06 | 渠道执行 | 只有获得批准的活动才能标记已执行；记录真实链接或执行凭证 |
| AC-07 | 增长报表 | 数据来源清晰；零访问显示 0，报名不计为支付用户 |
| AC-08 | MiMo 调用失败 | 可以查看错误、重试和原来已保存的成果，不出现重复发布 |
| AC-09 | 真实经营订单 | 报价、支付状态、交付状态分别存在；未支付不能显示收入 |
| AC-10 | 客户权限 | A 客户无法看到 B 客户的订单、表单数据和未公开文档 |
| AC-11 | 交付报告 | 包含目标、证据、执行动作、真实指标、下一步建议及生成时间 |
| AC-12 | 展示 Agent 协作 | 可以指出每个环节由哪位 Agent 处理，Agent 之间何时打回及原因，以及人何时批准或驳回 |
| AC-13 | Strategy 打回 Research | 证据不足时生成具体补查请求；补查后新旧证据都在，后台能看到两次任务的关联和原因 |
| AC-14 | 打回次数到上限 | 不再继续调用模型，项目进入“等待老板裁决”，老板能看到原因并做选择 |
| AC-15 | 打回后定位改变 | 原有定位确认失效，项目回到“等待定位确认”；基于旧定位的页面不能发布 |
| AC-16 | 声明缺少证据 | 声明未绑定证据、证据不存在或不可使用时不能送审，系统指出具体声明 |
| AC-17 | 反面证据处理 | 每个候选人群都有反向检索记录；有反面证据未回应时不能送老板确认；未找到时显示检索范围 |
| AC-18 | 实验样本不足 | 显示“样本不足”，不触发打回，不写成假设已被证实或否定 |
| AC-19 | 两道审批 | 老板已把关但客户未确认时不能发布；`decisions` 能看到两道记录和 `actor_role` |
| AC-20 | 项目专属链接 | 链接不可猜；错误或已作废的链接看不到任何项目数据 |
| AC-21 | 付费证据等级 | 有官网定价的竞品至少显示 E 级；评分和下载量标为信号；所有来源都查不到才显示“未知” |
| AC-22 | 证据写入 | Agent 不能直接写库；`search_evidence` 核对失败的内容不能标为已验证 |
| AC-23 | 公网访问 | 验证页在国内手机网络和美国节点都能打开 |
| AC-24 | 备用模型 | MiMo 故障切换其他模型时，`agent_tasks` 和经营台显示实际模型 |

**比赛最低通过标准：** 至少一位经许可的真实客户或试用者，走通一次“客户问题 → 市场分析 → 人工选择 → 页面发布 → 真实事件 → 结果复盘”，并留存完整执行证据。只用自有产品跑通时必须如实标注，不算达到这条标准。

# 11. JUNCTION CHINA 2026 比赛执行计划

## 11.1 为什么这个方案适合 Xiaomi MiMo OPC

赛题希望看到：一个人主导公司，多名 MiMo Agent 协作，把真实工作变成可交付成果。根据用户提供的赛题截图，评分重点是**创新性 35、商业化潜力 25、完成度 25、原创性 15**。

首客应该展示的不是“Agent 名字很多”，而是**一个人做老板，MiMo 研究市场、制定方案、制作页面、执行增长实验，Agent 之间会因证据不足互相打回，并且每一步可核查**。

## 11.2 赛前准备

| 时间 | 要完成的工作 | 验收点 |
|---|---|---|
| 11 月 5 日（周四）上午前 | 读 Hacker Login 里的赛题细则，确认赛前准备规则和报名状态 | 知道哪些内容可以提前做、如何披露 |

## 11.3 40 小时排期

官方开发时间为 11 月 6 日周五 19:00 至 11 月 8 日周日 17:30（北京时间），共 46.5 小时。下表按 40 小时安排，其余时间用于休息和缓冲。

| 时间 | 要完成的工作 | 验收点 |
|---|---|---|
| 0–4 小时 | 与赛前约好的客户确认唯一的标准服务、核心指标和实验判定标准；部署环境跑通 | 有真实需求记录、报价、交付范围和写好的判定标准 |
| 4–12 小时 | 官网、创建项目、业务存储、英文页面模板 | 能跑通订单/任务输入并预览页面 |
| 12–22 小时 | 接入 MiMo 四角色、证据库工具、反向检索、打回路由、声明检查、两道审批、错误恢复 | 能从需求研究走到可发布页面；打回和声明检查都实际运行过 |
| 22–30 小时 | 发布一张真实英文页面并执行一个经批准的渠道实验 | 有公开链接、执行记录和真实事件 |
| 30–36 小时 | 质量测试、数据复盘、客户交付与经营记录 | 数据和订单状态无混淆，报告可交付 |
| 36–40 小时 | 录屏、跑 Demo、整理运营证据和答辩 | 3 分钟讲完完整业务故事 |

**第 22 小时止损线：** 如果核心流程还没跑通，停止开发新功能，只解决一笔业务的端到端成功路径。打回功能按这个顺序简化：先把 Growth → Strategy 改为复盘里的文字建议，再把 Launch → Strategy 改为直接转老板；Strategy → Research 打回、声明检查和反向检索尽量保留。

## 11.4 发布窗口和实验判定

第 22–30 小时对应北京时间周六 17:00 到周日 01:00，也就是美国太平洋时间周六 01:00–09:00。比赛期的美国流量基本只有一个周六，访问量可能只有个位数到几十（这是估计，没有数据支撑）。

1. **赛前先跑一轮：** 规则允许时，人工跑一遍，不写产品代码，选美国工作日发布，数据标注“赛前”。美国周四白天约为北京时间周五 01:00–09:00。
2. **发布前写好判定标准：** 例如“50 次访问内至少 3 个有效留资”（数字仅为示例）。标准写进实验计划，并经老板把关、客户确认。
3. **样本不足就如实说：** 没到预设样本量时，结论只写“样本不足”。
4. **真实反馈放在前面：** 复盘报告先放真实回复和评论，再放转化率。

## 11.5 现场三分钟演示

- **第 0–30 秒：** 介绍一位真实中国开发者客户及其出海难题，展示首客接受了什么订单。
- **第 30–75 秒：** MiMo Research Agent 拿出有来源的目标人群、竞品证据和反面证据；Strategy Agent 发现证据不足，打回补查；补查回来后，老板把关并推荐，客户确认目标细分客户。
- **第 75–120 秒：** Launch Agent 生成英文页面，展示一条缺证据的声明被拦下；修改并经老板把关、客户确认后发布，演示真实 CTA 和表单，展示已批准的渠道任务。
- **第 120–155 秒：** Growth Agent 读取真实访问/留资数据，给出有约束的复盘建议。
- **第 155–180 秒：** 打开 OPC 经营台，展示服务订单、支付状态、Agent 执行记录、打回记录及成本，说明哪些决定由人完成。

所有示例收入、客户反馈和推广数据均须区别于真实数据；模拟案例必须清楚标注。研究阶段回放已跑好的真实记录，只现场跑“决策后重新生成文案”这一小段，并备一份录屏。客户确认无法在现场发生时，回放真实记录。打回和拦截环节同样可以回放真实运行记录；如果真实项目没有自然发生，可用测试案例演示，但必须标注，不能说成真实项目中发生的。

## 11.6 比赛与长期产品的关系

比赛要证明“这家公司真的能运转一次”；赛后才去证明“这家公司是否有重复购买、规模化运营和稳定盈利的能力”。不能把 40 小时内的一次实验包装成长期增长已经成立。

# 12. 产品成功的判断方法

## 12.1 首客公司的经营指标

真实咨询人数、有效报价数、付费订单数、已确认营业收入、每单交付成本、每单老板人工分钟、平均交付耗时、客户满意度及重复购买意愿。

## 12.2 首客帮助客户获得的增长指标

实际页面访问、CTA 点击、有效邮箱线索、试用申请、实际付费客户。统计需要标明时间范围，且线索/报名与付费之间有明确区别。

## 12.3 Agent 系统运行指标

任务成功率、失败和重试次数、打回次数及打回后结论是否改变、等待人工审批时间、模型费用、可追溯来源覆盖情况、事实声明的证据覆盖率、反面证据回应率，以及是否发生未经授权的发布。

## 12.4 初期成功门槛

不预设虚构的增长结果。比赛期的阶段目标是**跑通一笔真实客户服务并交付一个可公开验证的增长实验**。产品正式运营后再根据真实流量、成本和付费数据决定是否扩大规模。

# 13. 团队实施约定与待确认事项

**最重要的五个约定：**

1. 一开始只选择一个客户、一种主要服务、一个目标市场和一个推广渠道。
2. 每个 Agent 都要有明确输入、输出、失败规则与真实运行日志。
3. 页面必须能打开，表单必须能提交；可运行优先于美术特效。
4. 先做人工确认和真实数据记录，再考虑自动投放、复杂编排和多渠道扩展。
5. 参赛时清楚说明哪些功能是比赛现场开发、哪些是提前准备、哪些是未来规划；真实人员贡献与 Agent 执行分开表述。

## 附录 B：专业术语解释

- **OPC：** One Person Company，一人公司。本赛题强调一位经营者组织 AI Agent 完成真实运营。
- **Agent：** 能根据明确目标调用工具、完成任务并交付结果的 AI 助手。
- **ICP：** 理想客户画像，指最适合先服务的一小群具体用户。
- **MVP：** 最小可行产品，先解决最核心的一个问题，用于快速验证。
- **GTM：** Go-to-Market，产品进入市场、触达客户并争取成交的过程。
- **MRR：** 每月经常性收入；不能把竞品标价、意向登记或估算当作已验证 MRR。
- **CTA：** 行动按钮，例如“预约演示”“申请试用”。
- **打回：** 下游 Agent 发现输入不足，带着具体要求退回上游处理。
- **证据闸门：** 由程序执行的检查，证据或声明不合格时不能进入下一步。
- **反面证据：** 不利于当前判断的材料，例如差评、退订原因和价格抱怨。
- **付费证据等级：** 用 A 到 E 和“未知”表示产品收费或收入证据的强弱，不等于收入金额。
